## 核心内容

这是一份扣子 AI 新闻应用从抓取、清洗、日报生成、页面读取、UI 绑定到发布验收的完整复盘。最重要的不是某个抓取代码，而是形成了一套分层排错的方法：**先验证数据源，再验证工作流输出，再验证页面事件和组件绑定，最后验证真实发布版本。**

原项目经历过“工作流有数据但页面只显示演示内容、旧工作流引用失效、列表类型错误、页面一直转圈、动态摘要溢出”等问题，最终把采集链和页面读取链分开，使用 `Read_data` 给 UI 提供稳定数据。

## 一、最终架构

```text
资讯采集链路
公开新闻源
  → 抓取或插件节点
  → 字段清洗、合并、去重
  → 大模型生成日报摘要
  → 保存或输出结构化新闻

页面读取链路
首页加载事件
  → 运行 Read_data
  → output: Array<Object>
  → daily_report: String
  → 摘要组件 + 新闻列表组件
```

把两条链路分开的好处：

- 抓取失败时可以单独排查采集层。
- 页面只依赖稳定的 `Read_data`，不需要知道多个抓取节点的内部结构。
- UI、工作流和数据源可以分别测试，不会一改就全乱。

## 二、先定义数据契约

所有新闻来源统一转换为下面五个字段：

```text
title, link, picture, author, time
```

单条数据结构：

```json
{
  "title": "新闻标题",
  "link": "https://example.com/news",
  "picture": "https://example.com/image.jpg",
  "author": "作者",
  "time": "2026-08-14 10:21:51"
}
```

工作流结束节点必须明确声明：

| 输出字段 | 类型 | 用途 |
|---|---|---|
| `output` | `Array<Object>` | 新闻列表 |
| `daily_report` | `String` | 首页日报摘要 |

列表失败时，先检查数据是不是对象数组，不要先改 UI 样式。

## 三、开发过程中的关键修复

| 现象 | 根因 | 修复方法 |
|---|---|---|
| `ModuleNotFoundError: typings...` | 复制了其他节点自动生成的类型导入 | 使用当前节点自动生成的导入；必要时重建节点 |
| 代码加载就发网络请求 | `requests.get()` 写在模块顶层 | 把请求放进函数或 `handler` |
| 函数参数无效 | 函数读取全局 `response`，没有使用传入 URL | 函数内部按当前 URL 发请求 |
| Cookie 易失效且有泄露风险 | Cookie 被硬编码进源码 | 删除硬编码；鉴权时使用安全变量 |
| 日志巨大 | 打印完整响应或 BeautifulSoup 文档 | 只记录状态、数量和错误类型 |
| 列表要求 Array，实际是 Undefined | 页面不存在 `news_data` 变量 | 绑定真实工作流返回路径 |
| 页面引用不存在的 `AI_Info` | 工作流改名或删除后，UI 仍保留旧表达式 | 全面搜索旧名称并统一改绑 `Read_data` |
| 工作流成功但页面没数据 | 首页加载事件没有运行工作流 | 在页面加载事件中调用 `Read_data` |
| 页面有三条新闻但并非真实数据 | 使用固定默认 JSON 测试布局 | 改绑真实输出，并验证标题随数据变化 |
| 页面一直转圈 | Loading 永久为 `true` 或失败后未结束 | 绑定真实加载状态，成功和失败都要结束 |
| 组件不显示 | 把“隐藏条件”误当成“显示条件” | 不隐藏时设为 `false` |
| 摘要文字穿出卡片 | 动态文本使用固定高度 | 改为适应内容，或配最大行数和省略号 |
| 线上仍是旧页面 | 只保存草稿，没有发布新版本 | 检查打包、审核和目标渠道三项状态 |

## 四、抓取代码的可靠结构

抓取节点应遵守下面几条：

1. 当前节点的 `typings` 导入由扣子自动生成，不跨节点复制。
2. 网络请求放进函数或 `handler`，不在模块加载时执行。
3. 设置超时并调用 `raise_for_status()`。
4. 用 `urljoin()` 把相对链接和图片地址转为绝对地址。
5. 网络失败不能破坏全部数据链路。
6. 日志不打印 Cookie、令牌、完整响应正文和个人信息。

示意结构：

```python
def scrape_news(url: str) -> list[dict]:
    response = requests.get(url, headers=headers, timeout=15)
    response.raise_for_status()
    # 解析后统一返回 title/link/picture/author/time
    return result


def handler(args: Args):
    url = getattr(args.input, "url", "") or DEFAULT_URL
    news = scrape_news(url)
    args.logger.info(f"抓取完成，共 {len(news)} 条")
    return {"news": news}
```

## 五、`Read_data` 与 UI Builder 绑定

`Read_data` 的职责是读取最新新闻和日报，向页面返回固定结构。页面组件的最终绑定关系：

| 组件 | 表达式 | 说明 |
|---|---|---|
| 摘要文本 `Text1` | `{{Read_data.data.daily_report}}` | 日报正文 |
| 新闻列表 `List1` | `{{Read_data.data.output}}` | 新闻对象数组 |
| 列表图片 `Image2` | `{{item.picture}}` | 当前新闻图片 |
| 列表标题 `Text3` | `{{item.title}}` | 当前新闻标题 |
| 列表时间 `Text4` | `{{item.time}}` | 当前新闻时间 |

关键规则：

- 页面加载事件必须先运行 `Read_data`。
- `List1` 绑定整个数组。
- `item.xxx` 只能在列表项内部使用。
- 工作流改名后，要检查页面事件、数据绑定、显示条件和组件事件里的旧引用。

## 六、四种页面状态都要测试

| 状态 | 页面要求 |
|---|---|
| 加载中 | 显示加载提示，但不能永久转圈 |
| 成功且有数据 | 显示真实工作流标题和摘要 |
| 成功但为空 | 给出空状态，不应报 Undefined |
| 工作流失败 | 显示失败提示，并结束 Loading |

动态摘要默认应使用“适应内容”。若必须固定卡片高度，就要限制最大行数并显示省略号，不能让文字覆盖下面的列表。

## 七、真实数据验收

默认 JSON 只能验证布局，不能证明数据已经接通。真实联动至少满足：

1. 页面加载后确实运行 `Read_data`。
2. 列表绑定 `{{Read_data.data.output}}`。
3. 预览标题与工作流当前返回结果一致。
4. 刷新或修改数据后，页面标题随之变化。
5. 错误面板没有 `Undefined` 或“工作流不存在”。
6. 等待异步加载完成后再验收，不能用刚打开页面的截图下结论。

## 八、发布闭环

保存和预览都不等于上线。发布必须检查：

```text
应用打包完成
  ↓
扣子审核通过
  ↓
目标渠道发布成功
  ↓
发布后再次打开预览确认
```

原文记录的版本演进：

| 版本 | 主要变化 |
|---|---|
| `v0.0.5` | `Read_data`、真实列表绑定、加载显示修复 |
| `v0.0.6` | 首页视觉改版 |
| `v0.0.7` | 摘要卡自适应高度，修复长文本溢出 |

## 九、新闻摘要提示词原则

- 输入是公开来源的候选资讯，不代表已经完成事实核验。
- 使用“据输入来源称”“候选资讯显示”等归属表达。
- 不补充输入里没有的数字、结论和引语。
- 夸张或无法确认的内容标为“待核验”。
- 把摘要生成和事实核验分成不同任务。
- 在提示词中提供当前日期，减少模型对新信息的误判。

## 十、安全与长期维护

> [!warning] 凭据保护
> 不要在源码、日志、截图或知识卡中保存真实 Cookie、令牌、密码和完整请求头。若调试时已经暴露，应立即撤销并重新生成。

长期风险：

| 风险 | 处理方向 |
|---|---|
| 上游网页结构变化 | 新闻突然变成 0 条时，先检查 HTML 和 CSS 选择器 |
| 图片外链失效或防盗链 | 使用占位图；必要时转存到合规、稳定的对象存储 |
| 摘要重复、拒绝或夸张 | 调整提示词，加入日期、来源归属和禁止编造要求 |
| 定时任务不可靠 | 单独验证触发时间、失败重试、去重和数据保留周期 |
| 高频抓取带来合规问题 | 遵守网站条款、robots 规则和合理访问频率 |

## 十一、维护排错顺序

```text
1. 数据源网页能否访问
2. 抓取节点是否返回数组
3. 聚合节点是否把数组变成空值或字符串
4. 结束节点是否仍为 Array<Object>
5. Read_data 是否返回 output 和 daily_report
6. 首页加载事件是否运行 Read_data
7. List1 是否绑定 Read_data.data.output
8. 隐藏条件和 Loading 是否正确
9. 等待异步加载后是否出现真实标题
10. 当前查看的是草稿还是已发布版本
```

这套顺序从数据源查到发布层，能避免“页面没数据就乱改样式”或“工作流正确却反复重写抓取代码”。

## 这条知识对我有什么用

这张卡把扣子应用开发拆成数据、工作流、页面和发布四层，非常适合作为你学习自动化应用开发的实战模板。以后做股票新闻、网络安全资讯、AI 日报或自媒体热点应用，都可以复用“统一字段→采集清洗→稳定读取→UI绑定→分层验收”的骨架。

具体建议：下一次复用时先只接一个新闻源、只返回一条数据，跑通 `Array<Object>` 和页面加载事件；确认真实标题显示后，再增加第二个来源、日报模型和定时更新。
